## problem

Tables that do not include an `id` make it difficult to look up individual records.

```sql
-- bad
CREATE TABLE my_table(
  name TEXT
);
```

Additionally, tables that use a combintion of fields for its primary key make reference entries across tables more difficult, as each table must retain what constitutes a primary key in the table it is referencing.

```sql
CREATE TABLE memberships(
  org_id BIGINT NOT NULL,
  user_id BIGINT NOT NULL,
  
  PRIMARY KEY (org_id, user_id)
);

CREATE TABLE membership_metadata (
  user_id BIGINT NOT NULL,
  org_id BIGINT NOT NULL,
  metadata JSONB,
  
  PRIMARY KEY (org_id, user_id),
  -- bad
  FOREIGN KEY (user_id, org_id) REFERENCES memberships (user_id, org_id)
);
```

## solution

Add field `id` with the following properties:

- `BIGINT`: 64-bit integer, unlikely to exhaust values
- `GENERATED BY DEFAULT AS IDENTITY`: auto-increment value on each insert, while still allowing value to be provided (e.g. for backfill or restore)
- `PRIMARY KEY`: always the primary key of the table

```sql
-- good
CREATE TABLE my_table(
  id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  name TEXT
);
```

This also solves the issue of primary keys consisting of multiple fields. Even though using `id` as the primary key requires an additional uniqueness constraint, the cost at insert is less than the complexity of referencing primary keys that use multiple fields across tables.

```sql
CREATE TABLE memberships(
  id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  org_id BIGINT NOT NULL,
  user_id BIGINT NOT NULL,
  UNIQUE (org_id, user_id)
);

CREATE TABLE membership_metadata (
  membership_id BIGINT PRIMARY KEY,
  metadata JSONB,
 
  -- good 
  FOREIGN KEY (membership_id) REFERENCES memberships (id)
);
```
